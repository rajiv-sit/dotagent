DotAgent User Guide

Operational manual for moving from setup to a full engineering workflow: epics, Jira, codebase digestion, planning, implementation, peer review, validation, and evidence.

Workflow Map

1. Bootstrap
Install DotAgent and create project docs.
2. Epics and Stories
Turn objectives into traceable work.
3. Jira Intake
Interpret tickets, priorities, and dependencies.
4. Codebase Digest
Build context from source, tests, and docs.
5. Planning
Create a deterministic execution plan.
6. Implementation
Execute milestone by milestone.
7. Review and Validation
Respond to feedback and verify behavior.
8. Evidence
Produce auditable artifacts and reports.

1. Bootstrap a Project

Run these commands from the target project root after the dotagent/ source pack is present:

powershell -ExecutionPolicy Bypass -File .\dotagent\scripts\install-dotagent.ps1 -ProjectRoot .
powershell -ExecutionPolicy Bypass -File .\.agent\scripts\init-project-docs.ps1 -ProjectRoot .
powershell -ExecutionPolicy Bypass -File .\.agent\scripts\dotagent.ps1 setup

This creates the operating surface for the assistant: AGENTS.md, CONTEXT.md, PLAN.md, .agent/, and docs/design/. Setup is not the end state. It is the starting point for the lifecycle below.

Before asking for implementation, ask the assistant to read AGENTS.md, CONTEXT.md, PLAN.md, and docs/design/.

2. Epic and Story Generation

Derive Epics From Objectives

Start with a business objective, product requirement, incident theme, or platform goal. Ask DotAgent to identify the durable outcomes, system boundaries, users, constraints, and measurable success criteria.

Read AGENTS.md, CONTEXT.md, PLAN.md, and docs/design/.
Objective:
<paste product objective or requirement>

Generate candidate epics with:
- business outcome
- user or system actor
- affected systems
- functional scope
- non-functional constraints
- dependencies
- measurable acceptance signals

Decompose Epics Into Stories

Each story should be independently reviewable and traceable. Prefer small stories with explicit acceptance criteria, validation commands, and expected artifacts.

FieldPurpose
Story IDStable identifier, usually Jira key or local prefix.
User/System GoalWho benefits and what outcome is needed.
Functional RequirementsInputs, outputs, state changes, and interactions.
Non-Functional RequirementsPerformance, reliability, security, determinism, scalability, and resource constraints.
Acceptance CriteriaObservable conditions that prove the story is complete.
Trace LinksReferences to requirements, architecture, code modules, tests, and evidence.
 
Decompose epic <EPIC-ID> into traceable user stories.
For each story include:
- story title
- user/system value
- functional requirements
- non-functional requirements
- acceptance criteria
- dependencies
- validation commands
- expected evidence artifacts

3. Jira Integration and Interpretation

DotAgent can work from pasted Jira content or from connected tooling when available. The important step is to normalize Jira artifacts into local, assistant-readable context.

Ingest Jira Tickets

Read AGENTS.md, CONTEXT.md, PLAN.md, and docs/design/.
Jira ticket:
<paste epic, story, task, comments, acceptance criteria, links, and priority>

Interpret this ticket and produce docs/plans/<feature-name>-plan.md.
Include:
- ticket summary
- acceptance criteria
- dependencies and blockers
- priority and risk
- system requirements mapping
- architecture impact
- implementation milestones
- validation plan

Interpret Jira Fields

  • Summary and description: derive intent, scope, and system boundary.
  • Acceptance criteria: convert into validation checks and tests.
  • Priority: influence sequencing, not correctness.
  • Dependencies: identify prerequisite code, data, API, design, or team decisions.
  • Comments: extract late-breaking decisions and unresolved questions.
  • Linked issues: map upstream epics, related defects, and downstream tasks.

Do not implement from a Jira title alone. Ask DotAgent to identify missing acceptance criteria, unknown dependencies, and assumptions before coding.

4. Codebase Digestion and Context Building

For existing projects, ask DotAgent to digest the repository before planning. The digest should connect source structure to requirements and Jira stories.

Recommended Prompt

Digest this codebase for story <JIRA-ID>.
Read AGENTS.md, CONTEXT.md, PLAN.md, docs/design/, package/build files, source modules, tests, and existing docs.

Produce docs/plans/<feature-name>-codebase-digest.md with:
- module map
- key dependencies
- current implementation relevant to the story
- tests already covering the area
- gaps and partial implementations
- technical debt and risk
- files likely to change

What to Analyze

  • Static structure: folders, modules, packages, entry points, and public APIs.
  • Dependency graph: framework dependencies, local module imports, external services, data stores, queues, and build tools.
  • Existing behavior: code paths, tests, fixtures, configuration, logs, and generated artifacts.
  • Traceability: which implementation already satisfies Jira acceptance criteria and which criteria are unmet.
  • Debt: duplication, missing tests, brittle boundaries, unsafe error handling, and unclear ownership.

5. Planning Phase

The plan is the bridge between Jira, codebase context, and implementation. Store feature plans under docs/plans/ so they can be reviewed and updated.

Plan Contents

SectionRequired Content
ObjectiveWhat this feature, fix, or task must accomplish.
InputsJira links, requirements, design docs, existing code references, and assumptions.
MilestonesSequenced units of work with exit criteria.
Traceability MatrixJira item to requirement to code to test to evidence.
ValidationCommands, expected outputs, coverage expectations, and manual checks.
RisksKnown risks, mitigations, rollback notes, and open questions.
 
Using the Jira interpretation and codebase digest, generate docs/plans/<feature-name>-plan.md.
The plan must include:
- deterministic milestone order
- task breakdown
- file-level impact
- test strategy
- validation criteria
- expected outputs
- traceability from Jira to code and tests
- risks, assumptions, and rollback notes

6. Implementation Workflow

Implementation starts only after the feature plan is clear. Work one milestone at a time and keep evidence current.

Create a Branch and Execute

Read docs/plans/<feature-name>-plan.md.
Create branch feature/<feature-name>.
Implement milestone 1 only.
Run the milestone validation commands.
Fix failures.
Update PLAN.md with progress and evidence.
Then continue to the next milestone.

Maintain Traceability

  • Reference Jira IDs in branch names, commits, plans, tests, and PR summaries when possible.
  • Update PLAN.md when milestone status changes.
  • Update CONTEXT.md when a durable decision, constraint, risk, or architecture fact changes.
  • Keep code changes aligned with docs/design/Requirement.md, Architecture.md, HLD.md, DD.md, and milestone.md.

7. Peer Review and Validation

Structured Peer Review

Review this branch against the feature plan and Jira acceptance criteria.
Focus on:
- correctness
- requirement coverage
- missing tests
- security and reliability risks
- regressions
- maintainability
- unclear assumptions

Return findings ordered by severity with file and line references.

Respond to Review Comments

Read the peer review comments below.
Address only actionable feedback.
Keep the diff minimal.
Run relevant validation after fixes.
Update the plan or context only if project state changed.

Review comments:
<paste comments>

Pre-PR Validation

Ask DotAgent to run the project-specific checks and fix failures before preparing a PR.

Prepare this branch for PR.
Run:
- lint
- unit tests
- integration tests where available
- coverage
- pre-commit checks
- markdown link checks where available

Fix all failures.
Summarize commands, results, changed files, risks, and remaining gaps.

8. Evidence and Documentation

Evidence makes the workflow auditable and reproducible. Every meaningful change should leave a clear record of what was requested, what changed, and how it was validated.

Expected Artifacts

  • docs/plans/<feature-name>-plan.md: feature execution plan.
  • docs/plans/<feature-name>-codebase-digest.md: optional existing-code analysis.
  • docs/design/*.md: requirement, architecture, HLD, DD, and milestone updates.
  • PLAN.md: active progress and verification tracker.
  • CONTEXT.md: durable decisions and architecture facts.
  • Test output, coverage reports, lint results, screenshots, logs, or runtime evidence as appropriate for the project.

Full Lifecycle Prompt

Use this when you want DotAgent to perform the whole workflow from task intake to PR readiness.

Read AGENTS.md, CONTEXT.md, PLAN.md, and docs/design/.
Use Jira ticket <JIRA-ID> below.

Do the following:
1. Interpret the Jira ticket and acceptance criteria.
2. Digest the relevant codebase area.
3. Generate docs/plans/<feature-name>-plan.md.
4. Create branch feature/<feature-name>.
5. Implement the plan one milestone at a time.
6. Maintain traceability from Jira to requirements, code, tests, and evidence.
7. Run lint, tests, coverage, pre-commit, and markdown link checks where available.
8. Fix validation failures.
9. Update PLAN.md and CONTEXT.md if project state changed.
10. Prepare a PR summary with evidence, risks, and rollback notes.
